# Governance Consumption of Congestion Forecasts

## Overview

This document describes how governance consumes congestion forecast recommendations
generated by the `CongestionForecaster`. All recommendations are **ADVISORY ONLY** -
they require manual review and governance approval before any parameter changes.

## Signal Flow

```
┌─────────────────────┐
│  CongestionStats    │ ← Block observations
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ CongestionForecaster│ ← Threshold analysis
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ CongestionForecast  │ ← Contains recommendations
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ CongestionReporter  │ ← Creates AiSignalV1
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│   On-Chain Signal   │ ← Commitment published
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  Governance Review  │ ← MANUAL review required
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  Proposal Creation  │ ← Week 19: Governance voting
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  Approval & Execute │ ← Only after vote passes
└─────────────────────┘
```

## Recommendation Types

### 1. MIN_FEE Adjustment

**Signal Content:**
- `adjustment_pct`: Signed percentage change (e.g., +10%, -5%)
- `rationale`: Human-readable explanation

**Governance Action:**
1. Review the signal and supporting evidence
2. Verify congestion level matches recommendation
3. Create governance proposal (Week 19)
4. Submit for validator voting
5. Execute only if supermajority approves

### 2. BLOCK_SIZE_LIMIT Adjustment

**Signal Content:**
- `adjustment_pct`: Signed percentage change (e.g., +20%)
- `rationale`: Human-readable explanation

**Governance Action:**
Same flow as MIN_FEE - requires full governance approval.

## Evidence Provided

Each forecast includes supporting data:

| Field | Description |
|-------|-------------|
| `mempool_size` | Current mempool transaction count |
| `avg_mempool_size` | Rolling average mempool size |
| `mempool_growth_pct` | Current size as % of baseline |
| `block_fullness_pct` | Current block utilization % |
| `avg_block_fullness_pct` | Rolling average block fullness |
| `avg_fee` | Average transaction fee |
| `fee_p95` | 95th percentile fee |

## Congestion Levels

| Level | Threshold | Fee Recommendation | Block Size Recommendation |
|-------|-----------|-------------------|--------------------------|
| Low | <150% mempool, <70% blocks | -5% (if <30% avg fullness) | None |
| Moderate | ≥150% mempool OR ≥70% blocks | +10% | None |
| High | ≥200% mempool OR ≥85% blocks | +25% | +10% (if ≥80% avg fullness) |
| Critical | ≥300% mempool OR ≥95% blocks | +50% | +20% |

## Important Invariants

### What the System DOES:
- ✅ Collects mempool and block statistics
- ✅ Analyzes congestion trends
- ✅ Generates recommendations with rationale
- ✅ Publishes on-chain signals (CongestionForecast type)
- ✅ Stores detailed evidence off-chain

### What the System DOES NOT:
- ❌ Automatically modify MIN_FEE
- ❌ Automatically modify BLOCK_SIZE_LIMIT
- ❌ Execute any parameter changes
- ❌ Bypass governance approval
- ❌ Take any enforcement action

## Integration with Week 19 Governance

The governance module (Week 19) will:

1. **Query Signals**: Read CongestionForecast signals from chain
2. **Present to Validators**: Display recommendations in governance UI
3. **Create Proposals**: Convert recommendations to voteable proposals
4. **Voting**: Require supermajority (>2/3) for parameter changes
5. **Time Lock**: Enforce delay between approval and execution
6. **Execution**: Apply approved changes via governance executor

## Example Workflow

1. **Signal Published** (automatic):
   ```
   CongestionForecast {
     level: High,
     confidence: 180,
     fee_recommendation: Some(+25%),
     evidence: { mempool_growth: 220%, block_fullness: 88% }
   }
   ```

2. **Validator Reviews** (manual):
   - Views signal in governance dashboard
   - Verifies evidence matches observed conditions
   - Discusses with other validators

3. **Proposal Created** (manual):
   ```
   Proposal {
     type: ParameterChange,
     parameter: MIN_FEE,
     change: +25%,
     rationale: "CongestionForecast signal at height 12345",
     reference_signal: <signal_hash>
   }
   ```

4. **Voting Period** (governance process):
   - 7-day voting window (configurable)
   - Requires >2/3 validator approval
   - Quorum requirements apply

5. **Execution** (after approval):
   - Time-locked delay (e.g., 24 hours)
   - Parameter update applied
   - Event emitted for transparency

## Security Considerations

1. **No Automatic Changes**: The forecaster cannot modify parameters directly
2. **Governance Required**: All changes require validator voting
3. **Transparency**: All recommendations are on-chain and auditable
4. **Rate Limiting**: Governance can reject frequent change requests
5. **Rollback**: Parameters can be reverted via governance if needed
