# TODO: TypeScript SDK signing audit

**Status:** Open. Not blocking Python SDK delivery. Should be picked up as a separate audit task.

## Background

While researching the wire format for the Python SDK (Phase 0 of the
Week-37-style port), I traced the canonical signing path in
`crates/crypto/src/lib.rs` and compared it to what the existing SDKs do:

* **Rust SDK** (`sdk/novai-sdk/src/tx.rs`): calls `sign_tx_v1` from
  `novai_crypto`, which prepends the ASCII tag `b"NOVAI_TX_V1"` (11 bytes)
  to `encode_tx_v1_unsigned(tx)` and ed25519-signs the result.
  Source: `crates/crypto/src/lib.rs:179-186`.

* **TypeScript SDK** (`sdk/novai-sdk-ts/src/tx.ts:19-43`): assembles the
  same domain tag (`"NOVAI_TX_V1"` ASCII) followed by what it computes as
  `encodeTxV1Unsigned(tx)` and calls `tweetnacl.sign.detached(...)`.

The **signing schemes match** at the algorithm level: same domain tag,
same prepend-then-ed25519 pattern. The Python SDK Phase 1 commit ships
the same scheme and roundtrip-verifies it (143 unit tests passing).

## Why this still needs an audit

Even though the signing **schemes** match, the TypeScript SDK has **no
golden vector tests** that prove its byte-level output matches the Rust
encoder. Specifically the following risks remain unverified:

1. **u128 splitting**: TS encodes `u128` as two `setBigUint64()` calls
   with a manual high/low split. Off-by-one or endianness mistakes in
   that path would produce a signed tx whose `from`/`amount`/`balance`
   fields differ by a byte. The signature would look valid to TS but
   reject on-chain.

2. **Little-endian envelope vs big-endian payloads**: the Rust codec uses
   LE for the TxV1 envelope (`nonce`, `fee`, `payload_len`) and BE for
   payload-internal numeric fields. The TS SDK only ships tx-type
   builders 1-10 (Weeks 1-7); it has never been audited against any
   Week 28+ payload that uses both endiannesses in the same blob.

3. **Domain tag handling**: the TS SDK source comment says it uses
   `"NOVAI_TX_V1"` as an 11-byte ASCII prefix without a null terminator,
   which matches Rust. Confirmation would require comparing the exact
   bytes that go into `tweetnacl.sign.detached(...)` against the bytes
   that go into `ed25519_dalek::SigningKey::sign(...)` for at least one
   non-trivial transaction.

4. **Live chain submission**: there is no recorded instance of a TS-signed
   `novai_submitTransaction` call having been accepted by a node. If the
   TS encoder has any wire-format drift, no one would have noticed because
   the TS SDK's only example (`sdk/novai-sdk-ts/examples/quick-start`)
   does not appear to be part of a CI loop that hits a live node.

## Recommended audit steps

1. Use the Rust SDK's `examples/quick-start` to produce a known-good
   signed transfer transaction. Capture the hex-encoded signed bytes.
2. Reproduce the same transaction in TypeScript:
   * same seed (32-byte ed25519 seed in raw bytes),
   * same `from`, `pubkey`, `nonce`, `fee`, and `payload`.
3. Compare the TS-produced signed bytes byte-for-byte with the Rust
   bytes. They MUST be byte-identical.
4. Submit both to a local devnet via `novai_submitTransaction`. Both MUST
   return the same `txid` and land on chain.
5. Repeat for at least one Week 28+ payload that exercises a u128 field
   (e.g. `RegisterAiEntity` with a non-trivial `initial_balance`).
6. Once parity is confirmed, add a golden-vector test under
   `sdk/novai-sdk-ts/tests/` that locks the bytes for both transactions.

## What the Python SDK does in the meantime

The Python SDK (`sdk/novai-python-sdk/`) ships its own implementation of
`sign_tx_v1` that mirrors the Rust path exactly (`novai_sdk/crypto.py`),
plus a domain-tag verification test (`tests/test_crypto.py::TestSignTxV1::test_signing_uses_domain_tag`)
that confirms the signature does NOT verify against the unsigned bytes
without the `"NOVAI_TX_V1"` prefix. Phase 2 of the Python SDK adds
golden-vector tests against bytes generated by the Rust SDK; until those
land, the Python SDK guarantees parity by construction rather than by
test.

## Suggested owner

Whoever maintains the TypeScript SDK going forward. Until this audit
runs, do **not** promote the TS SDK as proof of multi-language wire-format
support in any external messaging.
